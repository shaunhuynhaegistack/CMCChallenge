# Reporting and observability

## What a run produces

```
reports/
  <browser>/
    cucumber-report.json        machine readable result, final attempt only
    cucumber-messages.ndjson    every attempt, used by the flaky detector
    html-report/index.html      human readable report
    screenshots/                full page screenshot of every failed attempt
    videos/                     recording of every failed scenario
    traces/                     Playwright trace of every failed attempt
  flaky-history.json            how often each scenario has needed a retry
performance/results/            k6 JSON, HTML and raw summaries
```

```bash
npm test && npm run report
open reports/chromium/html-report/index.html
```

The report from the latest run on `main` is published to GitHub Pages by the
`Publish the report site` job, in the same pipeline and directly after the report
it publishes: <https://shaunhuynhaegistack.github.io/CMCChallenge/>. It
carries all three engines and the k6 summaries, and `config/report/build-pages-site.ts`
writes the landing page over them. A committed snapshot of a real run - raw
results, k6 summaries and a failure screenshot - lives in
[`docs/sample-run/`](sample-run), so the reports can be read without opening the
Actions tab.

The HTML report is generated by `config/report/generate-html-report.ts`, which
discovers whichever browsers produced results rather than being told, so a single
browser run and a full matrix run both work with no flag. Failure screenshots are
attached to the failing step, so the report is self contained.

## Screenshots, videos and traces

All three are captured in `hooks/hooks.ts` and are on by default with
"keep on failure" semantics.

| Artifact | Default | Override |
| --- | --- | --- |
| Screenshot | Every failed attempt | always on |
| Video | Kept on failure, deleted on success | `VIDEO=on` keeps all, `VIDEO=off` disables |
| Trace | Kept on failure, discarded on success | `TRACE=on` keeps all, `TRACE=off` disables |

Playwright only writes a video when the browser context closes, which is why the
"keep or discard" decision runs in the very last After hook - Cucumber executes
After hooks in reverse declaration order, so that hook is declared first.

## Tagging strategy

Tags describe two independent things: **what** a scenario covers and **why** it
would be run.

| Tag | Meaning |
| --- | --- |
| `@smoke` | The shortest set that proves the application is usable. Runs on every commit. |
| `@regression` | Full functional coverage. Runs on pull requests and on main. |
| `@e2e` | Crosses more than one module and asserts through both the UI and the API. |
| `@api` | Asserts against the REST API. |
| `@auth`, `@pim`, `@rbac` | The functional area, one per feature file. |
| `@positive` / `@negative` | Happy path versus error handling. |
| `@flaky` | Quarantine. Excluded from the blocking run, still executed and reported. |
| `@showcase` / `@demo-failure` | The deliberate failure. Unreachable from any normal profile - see below. |

Rules that keep the tags useful:

* Area tags go on the `Feature`, not on each scenario - the whole file belongs to
  one area by construction.
* Every scenario carries exactly one of `@smoke` or `@regression`, so no scenario
  can be silently left out of both.
* `@flaky` is temporary and always paired with an issue. A tag that has been
  there for months means the scenario should be fixed or deleted.

```bash
npm run test:smoke
npm run test:all                                                  # all three engines
npm run test:chromium -- --tags "@pim and @negative"
npm run test:chromium -- --tags "@regression and not @flaky"
```

### The deliberate failure

`features/failure-showcase.feature` fails on purpose so the reports have a
failure to show. Every browser profile carries `tags: 'not @demo-failure'`, and a
profile's tag expression is **ANDed** with any `--tags` on the command line - so
it cannot be reached by adding a tag to a normal profile. It has its own
`showcase` profile, its own report folder, and a non-blocking CI job.

## Environment based execution

The environment is chosen with `ENV` and every value it defines can still be
overridden individually. See [architecture.md](architecture.md) for the full
precedence order.

```bash
ENV=demo npm test                       # public demo, no retries
ENV=ci npm test                         # longer timeouts, two retries, 4 workers
ENV=local BASE_URL=http://localhost:8080 npm test
BROWSER=firefox npm run test:firefox
```

On CI the same knobs are exposed through `Actions -> CI -> Run workflow`:
environment profile, the list of browsers, and a Cucumber tag expression.

## Slack and Teams notifications

`tools/notify.ts` turns the results under `reports/` into a message and posts it
to Slack, Teams, or both. It reads the same summary the job summary uses, so the
numbers always agree.

**Setup is one secret.** Nothing else has to change.

### Slack

1. <https://api.slack.com/apps> -> *Create New App* -> *From scratch*.
2. *Incoming Webhooks* -> enable -> *Add New Webhook to Workspace* -> pick the channel.
3. Copy the `https://hooks.slack.com/services/...` URL.
4. Repository -> *Settings* -> *Secrets and variables* -> *Actions* -> *New repository secret*
   named `SLACK_WEBHOOK_URL`.

### Teams

1. In the target channel: *⋯* -> *Workflows* -> template
   *Post to a channel when a webhook request is received*.
2. Finish the flow and copy the generated URL.
3. Add it as the repository secret `TEAMS_WEBHOOK_URL`.

The payload is an Adaptive Card, which is what the Workflows (Power Automate)
webhook expects. The older Office 365 connector URLs are being retired by
Microsoft, so the workflow route is the one worth setting up.

### Behaviour

* Neither secret set - the step logs that it is skipping and the job stays green.
* One set - only that channel is notified.
* A webhook rejects the request - a warning is logged and the job still reflects
  the real test result. A broken notification must never change a build result.

### Message contents

Repository, branch, browsers, environment, duration, start and end time, who
triggered the run, and either "all N scenarios passed" or the first five failures.
Two buttons link to the workflow run and to its artifacts.

Preview the exact payload without sending anything:

```bash
npm run notify:dry-run
```

Locally, put the webhook in `.env` (it is git ignored) and run `npm run notify`
after a suite.
